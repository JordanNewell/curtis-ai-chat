# Agents — scope (2026-10-09)

> Thesis: every agent gets **its own lane**; **Curtis coordinates** — so each worker serves its individual purpose, and any of them can be pressed into collaborative work without lanes ever blurring.

Named, reusable worker configs: a persona + model + tool ACL you can summon into any chat and hand to the swarm. Curtis becomes the neutral host — bring any model through any provider, give it a role, put it to work in the vault.

## The idea, sharpened

"Give every agent a role to play — they have the API, so Curtis becomes a player-coach: bring Grok, bring Cline, bring Claude, bring Codex through Curtis."

Honest framing first: Curtis cannot host *harnesses*. Cline, Codex CLI, and Claude Code are their own tool runtimes with their own IDE coupling — they don't embed. What Curtis hosts is the **role**: an OpenAI/Anthropic/xAI/Grok model behind a named persona with a toolset, running Curtis's agent loop against the vault. "Codex through Curtis" = an agent preset that points at OpenAI's codex models with a coding persona. That framing matters for marketing claims — sell roles, not ports of other products.

What an Agent **is** in v1:

```
Agent {
  id, name, emoji
  systemPrompt        // persona — layered, never replaces CORE
  providerId, modelId // per-agent model routing
  tools: { vault, web, mcp }   // ACL, three toggles
  temperature?, maxTokens?     // optional sampling overrides
  maxTurns?                    // optional override of the global agentMaxTurns
  memory: 'inherit' | 'on' | 'off'  // see Second pass §2 — not optional
}
```

What it is **not**: a new runtime, a separate process, a sub-harness. It resolves to (system prompt, provider, model, tool filter) at request time inside the existing loop.

## What already exists (and the gaps this fills)

| Piece | State | Gap agents fill |
|---|---|---|
| Agent mode (`src/core/tools.ts`, `src/main.ts` `callAgentLoop`) | Global toggle, global max-turns, 11 vault tools + web + MCP | Per-agent tool ACL; per-agent persona |
| System prompt (`src/core/system-prompt.ts`) | Global `settings.systemPrompt` via `/system`; CORE is non-negotiable by design | Per-conversation persona without clobbering the global prompt |
| Swarm (`src/swarm/index.ts`) | Leader spawns followers; followers **inherit the leader's model** and use a **hardcoded follower prompt** (`followerMessages()`, SWARM.md lists this as v1 limit #1) | Specialists: `spawn_agent({ task, agent: "researcher" })` |
| Arena (`docs/ARENA.md`) | One prompt → 2 models | Later: same *role*, 2 models |
| Multipane | Per-pane provider/model | Panes become views onto agents |
| Providers (`src/providers/`) | 27 built-in + custom + per-model sampling overrides | Already the hard part — agents ride on top |

The plumbing that must change is small and known: persona slot in `composeSystemPrompt()` (`src/core/system-prompt.ts:44`), tool filtering + provider/model resolution in `callAgentLoop` (`src/main.ts:735`), the send path (`src/chat/view.ts:2714`), `spawn_agent` params (`src/swarm/index.ts:74`), a new slash command (`src/chat/slash-commands.ts`), settings via the declarative `getSettingDefinitions()` API (hard constraint — see AGENTS.md).

## Redundant or useful?

**Personas alone are redundant.** Every chat app has custom instructions; "my snarky Grok bot" is table stakes, not a feature. If agents ship as only that, cut it.

**The combination is not redundant, and only Curtis can ship it:**

1. **Per-agent model routing** — an OpenAI-hosted app cannot route a role to Anthropic or Ollama. Vendors are single-provider by definition. The neutral host position is structural, not feature-copyable.
2. **Tool ACLs per role** — "Researcher" gets web but read-only vault; "Librarian" is local-only (Ollama, vault tools, zero network) and can provably never leak a private note to a cloud API. That last one is a privacy *product* claim, not a preset.
3. **Swarm specialists** — today's followers are clones of the leader (same model, same prompt). Agent-roster spawning turns the swarm from fan-out into a crew. This is the payoff that makes the entity worth having.
4. **One vault, one memory, one transcript format** — external tools each bring their own context silo. Agents share Curtis's memory, `@`-mentions, RAG, and markdown transcripts.

**Internal redundancy check:** agents absorb `/system` (which currently mutates the global prompt for everyone), resolve swarm v1 limitation #1 (per-follower models), and set up arena v2 (role vs role). No existing feature does what the entity does; `/system` gets demoted to "edit the default persona."

## Use cases, ranked

1. **Role presets with routing** — Editor (cloud model, read-only vault, tone passes), Researcher (web on, cloud), Critic (adversarial reviewer pane). Daily-driver value.
2. **Local-only private agent** — Ollama + vault tools + web off. The "my journal notes never leave this machine" agent. Strongest differentiator; marketable.
3. **Specialist swarm** — "Research this in parallel" spawns 3 Researchers, leader (a strong synthesizer model) combines. Cheap followers for reading, expensive leader for synthesis.
4. **Arena, same role, two models** — settle "which model edits my drafts better" with everything else held constant.
5. **Shareable crews** — export a preset (or a whole crew) as a markdown file with frontmatter; import like `.curt`. Growth loop.
6. **Pure persona bots** — the Grok-voice stuff. Shallow, but it's the on-ramp users understand; fine as free-tier content.

## Attack plan

### P1 — The entity + UI (the bulk)

- `src/types.ts`: `Agent` interface; `Conversation.agentId?: string` (+ denormalized agent name for transcript display); settings gains `agents: Agent[]`.
- New `src/agents/` module: store (CRUD over settings), resolution helper (`resolveAgent(conv | agentId) → { persona, providerId, modelId, tools, sampling }`).
- `src/core/system-prompt.ts`: `composeSystemPrompt(userExtension, agentPersona?)` — layering: date → CORE (never overridable, the harness contract stays) → agent persona → user global extension.
- `src/main.ts` `callAgentLoop`: accept resolved agent; filter the toolset by ACL (three toggles intersect the existing filter chain); provider/model resolution becomes per-conversation-agent aware (note: the follower path already threads `opts.providerId` — generalize it).
- `src/chat/view.ts` send path: resolve the conversation's agent on send; header pill shows the active agent (same slot as the 🔧 Tools pill); model picker reflects/overrides per-conversation.
- UI: Settings → Agents section (declarative settings + an editor modal: name, emoji, persona textarea, provider/model pickers reusing the model-picker machinery, three tool toggles, optional sampling overrides). `/agent` slash command: bare = picker, `/agent new`, `/agent off`. Ribbon/command-palette "New chat with agent…".
- Migration: none needed (additive); `/system` help text points at agents.

### P2 — Swarm specialists (the payoff)

- `spawn_agent` gains optional `agent` param (name or id, fuzzy); unknown name → tool error listing the roster.
- Leader's system prompt advertises the roster ("specialists available to spawn: …").
- `followerMessages()` in `src/swarm/index.ts` composes persona instead of the hardcoded prompt; follower tool ACL comes from the agent, intersected with the global toggles (`enableAgent`, `enableWebSearch`, `enableMcp`) — leaders have no ACL of their own to intersect.
- Cap behavior unchanged; follower conversations record `agentId` for display.

### P3 — Arena, sharing, polish

- Arena mode: pick an agent for each side (same role, different models).
- Export/import agent presets as markdown-with-frontmatter (fits memory/transcript file ethos; import path plugs into `src/import/`).
- Per-agent memory scoping — likely cut; shared global memory in v1 is the right default.
- Mobile pass: agent picker + persona editor on mobile settings.

Sizing: P1 is ~2–4 focused sessions (view.ts is 3.3k lines and owns the send path); P2 ~1; P3 ~1–2. Ship P1+P2 together as "Agents" — P1 without P2 is the redundant version.

## Open decisions

1. **Storage:** `settings.agents` (recommended v1 — fast, rides the declarative settings API, syncs like every other setting) vs. vault files `AI/Agents/*.md` (Obsidian-native, hand-editable, shareable — but CRUD-over-files costs more; P3 export gives the file story either way).
2. **Layering:** persona sits between CORE and user extension (recommended — CORE stays the harness contract; agent personas can't break tool behavior).
3. **Tool ACL granularity:** three toggles v1; per-tool and per-MCP-server allowlists later if asked.
4. **Per-agent memory:** shared global in v1; scoping is a P3 maybe.

## Second pass (2026-10-09, later)

Adversarial re-read of the above. Five corrections, one endgame answer, fences.

### 1. Attribution copies the provider/model pattern

`Conversation.provider/model` is the *current* pointer; every `ConversationMessage` records the provider/model that produced it. Agents must do exactly the same: `Conversation.agentId` = current agent, `AgentMessage.agentId` = who wrote that turn. This falls out of supporting **mid-conversation agent switching** (switch from Editor to Critic and keep the thread), and it quietly delivers 80% of the "round table" endgame for free — one transcript, multiple named workers, attribution per turn. Do not build round-table machinery in v1; see §6.

### 2. The memory hole (this was wrong in v1 of this doc)

The "local-only agent provably never leaks" claim is **false under shared memory**: a local agent reads a private note → memory capture (`auto` mode, silent) writes a fact to `AI/Curtis Memory.md` → the next cloud chat injects that fact. The note leaves the machine via the memory file, not the agent. Therefore `memory: 'inherit' | 'on' | 'off'` is a **P1 field**, not P3. The local-only preset ships with `memory: 'off'`, and the agent editor says so in plain text ("this agent does not read or write Curtis memory"). Memory capture mode stays global.

### 3. Storage rec stands; the *format* is the interop layer

Claude Code subagents are markdown files with YAML frontmatter (`name`, `description`, `tools`, `model`) + body = system prompt — and an ecosystem of shared agent files already exists. Keep `settings.agents` as the store (mobile-safe, atomic, rides the declarative settings API), but make P3's export/import speak a **compatible dialect**: import `.claude/agents/*.md` on day one ("bring your crew from Claude Code"), export to the same shape. Users' existing collections become Curtis's onboarding roster; nobody has to adopt a fifth format.

### 4. The default agent kills the `/system` special case

Don't materialize a "Default agent" entity. Resolution fallback: no `agentId` → persona = `settings.systemPrompt` (the existing global), `/system` keeps working untouched. Zero migration; the old global prompt is simply "the persona you get when no agent is active." One resolution rule, no UI special case.

### 5. Layering order flips

Earlier this doc put agent persona between CORE and the user extension. Wrong mental model: the global extension is the user's *standing orders to every agent* ("always answer in Vietnamese"), the persona is the *role*. Order: date → CORE (non-negotiable harness contract) → global extension → **agent persona last**. The role wins ties; standing orders survive role changes.

### 6. The endgame question — presets → orchestration → round table?

The literal user fantasy ("bring Grok, bring Claude into one room") is a round table: multiple agents as visible participants in one conversation. Built naively it's a Discord-bot gimmick — every agent sees the whole thread (token multiplication), turn-taking crosstalk, no task shape. The useful kernels of it are already covered: mid-conversation switching (§1) gives "second opinion in the same thread," arena gives "same prompt, two models," swarm gives "divide the work." If a round-table mode ever earns its build, the safe version is bounded debate: fixed N rounds, two named agents, a draft under critique, human closes it. Fence it until someone asks.

### 7. Naming collision with our own docs

"Agents" collides with **agent mode** (the tool loop, `docs/AGENT.md`) — "an agent" vs "agent mode" will confuse docs and support. Marketing gravity says Agents (Claude Code subagents, Cursor agents, GPTs); internal clarity says Roles. Call the feature **Agents** and fix the collision in docs: `AGENT.md` retitles to "Agent tools" (the loop), agents are "named workers" — INDEX.md gets one line drawing the distinction. Cheaper than inventing vocabulary the market won't search for.

### 8. Fences — not building

- Autonomous agent-to-agent loops without human pacing (see §6's bounded debate as the later, safe version).
- Curtis-as-MCP-server (exposing Curtis agents to other apps) — different product.
- Per-agent memory stores, per-agent RAG indexes — no demand signal, real complexity.
- In-plugin agent marketplace — curated crews live on the site; the plugin stays free and file-based.
- Spend caps/budgets — `maxTurns` per agent is the only guardrail in v1; budget machinery is its own feature.
- **GPT/Gem persona import** — OpenAI and Google exports carry chat text, not persona definitions (a ChatGPT export tags which chats used which GPT via gizmo id, but never the instructions). Stubbing an agent from chat grouping produces a named shell with nothing inside. Skip. The rebuild path is the builder: the user wrote those instructions once and can paste them into a persona. The P3 file format is the real "bring them here" play — portable agent files, Claude Code dialect first.

### Revised P1 checklist (delta)

- `Agent.memory` tri-state + `Agent.maxTurns?` in the type (done above).
- Message-level `agentId` attribution + conversation-level current agent.
- Resolution: fallback persona = `settings.systemPrompt`; layering CORE → global → persona.
- P3 import repointed: Claude Code agent files first-class, export second.

## Bootstrap: PCP on Curtis (2026-10-09, direction)

PCP (portable claim profiles — `.pcp` identity files, consent engine, federation, the orchestrator/"Human DNS") bootstraps here, with Curtis as the first real host of PCP identity. The fit is structural, not thematic:

| PCP component | What Curtis already has |
|---|---|
| Consent Engine (per-claim, per-requester) | Agent tool ACLs + memory tri-state — a hand-rolled 2-policy consent engine; the local-only-agent leak fix IS a consent decision |
| Claim injection into AI context | The memory block (`memoriesUsedIds` chip generalizes to "N claims") |
| Extraction pipeline | The swarm — specialists that read the vault and maintain claims as vault artifacts |
| Orchestrator `/claims` endpoint | Curtis is already an MCP **client** — a PCP orchestrator exposed as an MCP server is consumable with zero plugin code |

The ladder — each rung useful alone, no rung requires the next:

- **PCP-0 — claims as a vault artifact (local, read-only).** A `.pcp`/`PCP.md` file with structured claim sections (PEP-P personality, PEP-D developer, PEP-H health…). Agents inject the *consented subset* into context, extending the memory block. Policy = a local claims map on the Agent ("may read PEP-D, denied PEP-H"); most-restrictive-wins evaluated in `AgentManager`. No server, no OPA, no DID.
- **PCP-1 — consent-gated memory.** The memory tri-state graduates into per-agent claim-class policies; capture writes claims (with provenance, which MemoryFact already has) instead of flat facts. Audit trail = the transcript's injection record.
- **PCP-2 — extraction + freshness via swarm.** Leaders maintain the claims file: staleness review as a leader task, conflict strategies (recency / evidence weight / human resolution) applied to claim updates.
- **PCP-3 — the network.** Resolver, federation, DID-mTLS, audit server — built in the PCP project, never inside the plugin. Curtis consumes via MCP (`mcp__pcp__get_claims`); consent evaluation migrates server-side to preserve user sovereignty.

Fences: no orchestrator/OPA/DID code inside the plugin (vault-first, dependency-free holds); PCP-0/1 live in `AgentManager` as a claims policy, not a policy-engine port. This upgrades the agent story from "roles with permissions over the vault" to "roles with consent-governed identity" — the thing vendor-hosted agents structurally cannot offer.

**PCP-0 — SHIPPED 2026-10-09.** `src/agents/pcp.ts` (pure parser: class headings `PEP-*`, case-insensitive tokens, default-deny for unrecognized sections, 4k injection cap, first-section-wins dedupe) + `Agent.claims?: string[]` policy + `loadConsentedClaimsBlock()` in `AgentManager` + injection in `buildMessagesArray` + editor field ("Profile claims") + "Open / create…" settings row that seeds `AI/PCP.md` from a template. Settings gained `pcpFilePath` (default `AI/PCP.md`). 15 parser tests in `pcp.test.ts`. Not in PCP-0: swarm followers don't inject claims (consent semantics for delegation deferred to PCP-1), no claims chip on messages.
